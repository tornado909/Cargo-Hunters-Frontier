# CI и релизы Cargo Hunters Frontier

## Текущий контракт выпуска

Проверенный ABI: **Cargo Hunters 0.26.38.59**. В архиве находится **только папка BepInEx/plugins**: FrontierPack и три дополнительных Frontier-плагина. Teammate Flags — отдельный проект. BepInEx/core, IL2CPP interop, сохранения, Steam-данные, пользовательские конфиги и генерируемая FrontierPack/compiled не распространяются.

Каждый выпуск содержит:
- Cargo-Hunters-Frontier-vX.zip — архив с корнем BepInEx/
- BUILD-INFO.json — коммит, ABI, полный перечень пересобранных и готовых DLL, SHA256
- SHA256SUMS.txt — контрольные суммы архива и BUILD-INFO.json

## Что реально компилируется

Исходники в src/Plugins/ — **точные рабочие версии**:
- SurvivorExitGuard → Frontier.SurvivorExitGuard.dll
- SurvivorWearGuard → Frontier.SurvivorWearGuard.dll
- UniversalRepairKit → Frontier.UniversalRepairKit.dll

Все три плагина прошли контрольную сборку с референсами нужной версии игры и проверку SHA-256 относительно рабочих DLL.

Оставшиеся **32 DLL Frontier** не пересобираются этим процессом. Они включаются из точно проверенного рабочего снимка (235 файлов, 26 модулей, 197 проверенных записей манифестов). Текущие оригинальные исходники Core/Modular/Loot/Survivor и многих других модулей пока представлены не полностью. Нельзя незаметно подменять их устаревшими декомпилированными версиями.

Если часть исходников src/Engine, src/Reserve, src/Survivor или reconstruction изменится относительно контрольного коммита снимка, релизная сборка завершится ошибкой до упаковки. Это защитит от публикации архивов, содержащих неактуальные DLL.

## Защищённые входные данные

Референсы игры и рабочий снимок **не коммитятся в Git**. CI получает шифрованный входной архив из prerelease с техническим тегом ci-inputs-20261011. Расшифровка — только в одноразовой виртуальной машине GitHub-hosted runner с использованием секрета репозитория FRONTIER_CI_INPUTS_PASSPHRASE.

Внутри зашифрованных входных данных:
- 226 version-matched DLL для компиляции (BepInEx/core и interop)
- Проверенный production-снимок (без пользовательского профиля и генерации compiled)
- SHA256 каждого референса, каждого файла пакета и версия игры
- Коммит исходников, от которого разрешено использовать остальные prebuilt DLL

После сборки временные референсы удаляются. Ни private input, ни IL2CPP DLL не загружаются в Actions artifacts или релизные ZIP.

Для ротации набора: заново собрать снимок из **проверенной рабочей установки**, проверить версию игры и файлы, выполнить scripts/prepare-ci-inputs.py на отдельной сборочной машине, зашифровать новый tar.gz с новым случайным AES-256 паролем через GPG, загрузить новый зашифрованный asset в GitHub Release, изменить технический тег в workflow и обновить секрет через GitHub CLI (stdin). Никогда не добавлять расшифрованную копию и пароль в коммиты или логи.

## Как запустить

- **Actions → Build Frontier plugins and Release BepInEx → Run workflow**: ручная проверка, тестовый ZIP публикуется как GitHub Pre-release с техническим тегом ci-dryrun-<commit>. После проверки эту временную запись и её тег следует удалить. Actions artifacts не используются, поэтому квота их хранения не расходуется.
- **Git-тег vX** (например v0.1.0): Actions проводит те же проверки, компилирует три актуальных плагина и автоматически публикует ZIP + BUILD-INFO + SHA256SUMS в соответствующем GitHub Release.
- Обычный push/PR: только легковесные source checks; защищённые исходные данные не используются.

Для команд удобен GitHub CLI: gh workflow run build-release.yml --ref main и gh run list --workflow build-release.yml. **Тег не публиковать до зелёного тестового прогона.**

Релизный workflow имеет ограниченные триггеры: он **не** запускается на pull_request и выполняется на GitHub-hosted runner. Обычные проверки PR не получают сборочные секреты.

## Приёмка и ограничения

CI гарантирует сборку трёх проверенных исходных плагинов, соответствие input ABI, корректность манифестов и ZIP. CI **не** заменяет игровой тест: перед стабильным релизом необходимы ручные проверки хаба, режима Выживание, ремонта, сохранений и мультиплеерной синхронизации.

Пакет не должен считаться полным «собранным с нуля» исходным релизом. По мере восстановления исходников каждый модуль должен перейти из набора prebuilt в независимую сборку с тестами и проверкой соответствия DLL.
